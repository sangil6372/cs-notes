## 월요일 오전, 은행 창구

사람이 몰린다. 그런데 직원은 한 명뿐이다. 줄이 엄청 길어진다. 은행은 어떻게 할까? 직원을 늘린다.

좋다. 그런데 문제가 생긴다. 손님이 들어오자마자 **누구에게 가야 하지?** 창구1? 창구3? 손님은 모른다. 그래서 입구에 안내 직원이 있다.

<Said lines={[
  { who: "손님", text: "예금 업무 보러 왔는데요." },
  { who: "안내", text: "3번 창구로 가세요." },
]} />

이 안내 직원이 바로 **Load Balancer**다. Load는 업무량, Balance는 균형. 즉 업무를 골고루 나눈다.

서버가 한 대라면 100만 명이 몰려서 죽는다. 10대로 나누면 각각 10만 명씩. 훨씬 여유로워진다.

## 아무 서버나 보내도 될까?

Server 2가 고장 났다고 하자. Load Balancer는 생각한다. "얘는 죽었네. 보내지 말자."

<FanOut
  from="사용자"
  via="Load Balancer"
  targets={[
    { label: "Server 1" },
    { label: "Server 2", down: true },
    { label: "Server 3" },
    { label: "Server 4" },
  ]}
  caption="죽은 서버는 분산 대상에서 빠진다. 이게 Health Check."
/>

주기적으로 서버가 살아 있는지 확인하는 것, 이걸 **Health Check**라고 한다.

## URL을 보고 나눌 수도 있다

질문 하나. 이미지를 보내는 서버와 로그인을 처리하는 서버가 같아야 할까? 굳이 그럴 필요가 없다.

Load Balancer는 URL을 보고 보낼 수도 있다. `/logo.png`는 이미지 서버로, `/login`은 인증 서버로. 이걸 **L7 Load Balancing**이라고 한다.

L7? OSI 7계층이 여기서 나온다.

HTTP는 7계층이다. 즉 L7 로드밸런서는 HTTP 내용을 읽을 수 있고, 그래서 URL도 볼 수 있다.

반대로 **L4 Load Balancer**는 TCP만 본다. IP와 Port만 안다. 그래서 더 빠르지만 URL은 모른다.

## Reverse Proxy는 뭐가 다른가

먼저 Proxy부터. 프록시는 **대리인**이다. 사장이 직접 전화를 받지 않고 비서가 대신 받는 구조를 생각하면 된다.

그런데 프록시는 두 종류다.

**Forward Proxy**는 사용자 편이다. 나 → Proxy → 인터넷. 회사, 학교, 도서관에서 "직원이 어디에 접속했는지" 관리하기 좋다.

**Reverse Proxy**는 반대다. 사용자 → Proxy → 서버. 이번에는 **서버를 숨긴다.** 사용자는 실제 서버를 모른다.

연예인과 소속사를 생각하면 된다. 팬이 전화해도 연예인에게 바로 연결되지 않는다. 소속사가 받고, 걸러서 넘긴다.

### Reverse Proxy가 하는 일

- **서버 숨기기** — 실제 서버 IP를 노출하지 않는다.
- **SSL 종료** — HTTPS 복호화는 생각보다 무겁다. Proxy가 먼저 복호화하고 뒤로 넘긴다. (내부망에서는 HTTP를 쓰기도 하고, 내부도 HTTPS를 유지하기도 한다.)
- **캐시** — `logo.png` 같은 건 매번 웹 서버까지 갈 필요가 없다. Proxy가 기억했다가 바로 응답한다.
- **압축** — HTML, JSON을 압축해서 보낸다.
- **보안** — `../../etc/passwd` 같은 이상한 요청을 앞에서 막는다.

## 그래서 둘 중 누가 위인가?

정답은 **"상황에 따라 다르다."** 다만 현대 웹에서는 둘의 기능이 하나의 제품에 함께 들어있는 경우가 많다. Nginx, HAProxy, Envoy 같은 소프트웨어는 Reverse Proxy 역할도 하고 Load Balancer 역할도 한다.

즉 "로드 밸런서 = 리버스 프록시"는 틀린 말이고, <strong>"하나의 프로그램이 두 역할을 모두 할 수 있다"</strong>가 더 정확한 표현이다.

<Deeper>

- **프록시를 거치면 서버가 보는 클라이언트 IP가 바뀐다.** 웹 서버 입장에서 접속자는 전부 프록시 IP다. 그래서 프록시가 원래 IP를 `X-Forwarded-For` 헤더에 담아 넘긴다. 은행 접속 로그나 이상거래 탐지에서 이 설정이 빠지면 모든 거래가 같은 IP에서 온 것으로 기록된다.
- **Health Check도 수준이 있다.** TCP 연결만 되는지 보는 것과, `/health`를 호출해 DB까지 붙는지 확인하는 것은 다르다. 앞의 방식만 쓰면 프로세스는 떠 있는데 DB가 끊긴 서버로 계속 트래픽이 간다.
- **L7을 쓰면 세션 문제가 따라온다.** 요청마다 다른 서버로 가면 로그인 상태가 풀릴 수 있다. 그래서 같은 사용자를 같은 서버로 묶는 sticky session을 쓰거나, 아예 세션을 Redis 같은 외부 저장소로 빼서 서버를 무상태로 만든다. 후자가 정석이다.
- **로드밸런서 자체가 단일 장애점이 된다.** 앞단을 하나만 두면 그게 죽을 때 전부 죽는다. 그래서 VRRP 같은 방식으로 LB를 두 대 이상 이중화한다.

</Deeper>

앞에서 공부한 계정계 시스템이 이 맨 끝에 있다. 은행의 전체 구조가 여기서 하나로 연결된다.

<Key>

| 기술 | 핵심 역할 |
| --- | --- |
| Load Balancer | 여러 서버에 트래픽을 분산하고 장애 서버를 우회한다 |
| Reverse Proxy | 서버 앞에서 요청을 대신 받고 보안·캐시·SSL 종료를 수행한다 |
| Forward Proxy | 사용자 대신 인터넷에 접속한다 |

</Key>

지금까지 브라우저 → DNS → TCP → HTTPS → Load Balancer → 웹 서버까지 왔다. 그런데 아직 의문이 하나 남아 있다. **HTTPS는 도대체 어떻게 암호화를 하는 걸까?** 대칭키, 비대칭키, RSA, TLS, 인증서가 하나의 이야기로 연결되는 순간이다. "공개키로 암호화하고 개인키로 복호화"를 외우는 수준을 넘어, 브라우저가 서버를 어떻게 신뢰하는지까지.
