TCP는 왜
그렇게 동작하는가

외우는 대신 이유를 따라간다. 연결을 끊는 데 왜 네 번이 필요한지, 왜 처음부터 전속력으로 보내지 않는지, 그리고 왜 최신 웹은 TCP를 떠나기 시작했는지.

Chapter 15

TCP는 왜 헤어질 때는 네 번 인사할까?

대부분의 책은 이 장을 이렇게 끝낸다. SYN → SYN·ACK → ACK, 그리고 FIN → ACK → FIN → ACK. 그리고 외우라고 한다. 그런데 왜 시작은 세 번인데 끝은 네 번일까? 이 질문에 답할 수 있으면 TCP를 이해한 것이다.

먼저 사람으로 생각해 보자

친구와 통화 중이다. 이제 내가 먼저 끊고 싶다.

나나 먼저 끊을게.

친구응, 알겠어.

끝일까? 아니다. 상대도 아직 할 말이 있을 수 있다.

친구잠깐, 내일 몇 시에 볼래?

그러니까 "나 먼저 끊을게"와 "나도 이제 끊을게"는 같은 말이 아니다. 이게 핵심이다.

TCP 연결은 통로가 두 개다

우리는 연결을 하나의 선으로 상상하지만, 실제 TCP 연결은 방향이 다른 두 개의 통로로 이루어져 있다.

각각을 독립적으로 닫을 수 있다는 것 — 4-Way Handshake의 모든 이유가 여기서 나온다.

네 단계를 따라가 보자

첫 번째. 내가 더 이상 보낼 게 없다. FIN을 보낸다. Finish, 즉 "끝났습니다"라는 뜻이다. 상대는 ACK로 대답한다. "알겠습니다."

여기까지는 이 방향만 닫힌 것이다.

왜 반대 방향을 살려둘까? 서버는 아직 보낼 데이터가 남았을 수도 있기 때문이다. 파일 다운로드를 생각해 보자. 내가 FIN을 보내며 "난 요청 끝"이라고 말했는데, 서버는 아직 500MB를 보내는 중이다. 여기서 갑자기 끊어버리면 다운로드가 망한다.

그래서 서버는 ACK로 "알겠어, 근데 나 아직 보낼 거 있어"라고 답하고 전송을 마저 끝낸다.

두 번째. 전송이 다 끝나면 이번에는 서버가 FIN을 보낸다. "나도 끝." 마지막으로 내가 ACK로 대답한다. "응, 확인."

그런데 시작은 왜 세 번이었지?

연결을 시작할 때는 두 번째 단계에서 SYN과 ACK를 한 번에 합쳐 보냈다. 왜 합칠 수 있었을까?

그때는 상대가 연결을 받아들이는 동시에 자기도 연결을 원했기 때문이다. "네, 받았습니다"와 "저도 연결 원합니다"를 한 번에 말할 수 있었다.

하지만 종료는 다르다. 상대가 ACK를 보내는 순간에도 아직 데이터를 보낼 수 있다. 그래서 FIN을 바로 합칠 수 없다. 결국 따로 보낸다. 그래서 네 번이다.

Half Close — 한쪽만 끊기

여기서 아주 중요한 개념 하나. TCP는 한쪽 방향만 닫을 수 있다. 이걸 Half Close라고 한다. 보내는 것은 끝, 받는 것은 계속. 파일 다운로드나 로그 수신처럼 "요청은 끝났지만 응답은 계속 받아야 하는" 상황에서 실제로 쓰이는 구조다.

마지막 ACK를 보냈다. 끝났을까?

아직 아니다. TCP는 조금 기다린다. 혹시 마지막 ACK가 사라졌을 수도 있으니까. 이걸 TIME_WAIT이라고 한다.

택배기사배송 완료했습니다.

고객확인했습니다.

택배기사는 바로 가버리지 않는다. 혹시 고객이 "잠깐, 잘못 왔어요!"라고 말할 수도 있으니까. TCP도 똑같이 잠깐 기다린다.

개발자들이 자주 만나는 현상

프로그램을 껐는데 다시 실행하면 Address already in use 에러가 난다. "분명히 종료했는데 왜 포트가 아직 사용 중이지?" 바로 이 TIME_WAIT 때문인 경우가 많다. 운영체제가 혹시 늦게 도착하는 패킷이 없는지 잠시 연결 정보를 유지하고 있기 때문이다. 서버를 빠르게 재시작하거나 테스트를 반복할 때 자주 마주친다.

더 깊이
  • 4번이 항상은 아니다. 서버가 더 보낼 데이터가 없으면 ACK와 FIN을 한 세그먼트에 합쳐 보낸다. 그래서 실제 패킷 캡처를 뜨면 3개로 끝나는 경우도 흔하다. 4-Way는 "최대 네 번"이지 "항상 네 번"이 아니다.
  • TIME_WAIT은 먼저 끊은 쪽에만 생긴다. 능동 종료(active close)를 한 쪽이 2 × MSL(리눅스 기준 60초) 동안 상태를 유지한다. 서버 재시작 시 포트가 물려 있다면 그 서버가 먼저 끊었다는 뜻이고, 소켓에 SO_REUSEADDR를 걸면 해결된다.

TCP 연결의 일생

  1. 1연결 시작SYN → SYN+ACK → ACK
  2. 2데이터 전송패킷 → ACK → 패킷 → ACK …
  3. 3연결 종료FIN → ACK → FIN → ACK
  4. 4잠시 대기TIME_WAIT
  5. 5완전 종료CLOSED
오늘의 핵심

TCP는 연결을 하나의 선으로 보지 않는다. 내가 보내는 통로와 상대가 보내는 통로를 독립적으로 관리한다.

그래서 종료할 때는 "나는 끝"과 "나도 끝"이라는 두 개의 의사 표현이 필요하고, 그 결과가 4-Way Handshake다.

다음 장

그럼 인터넷은 도대체 얼마나 빠를 수 있을까? 패킷을 너무 많이 보내면 공유기가 터지고, 서버가 못 받고, 중간 라우터의 버퍼가 넘친다. 그런데 TCP는 신기하게도 상대가 감당할 수 있는 속도를 스스로 계산한다.

Chapter 16

TCP는 왜 처음부터 전속력으로 보내지 않을까?

대부분은 이렇게 외운다. "TCP는 흐름 제어를 한다. TCP는 혼잡 제어를 한다." 솔직히 하나도 와닿지 않는다. 오늘은 딱 하나의 질문으로 시작하자.

처음 가는 고속도로

오늘 처음 가는 길이다. 처음부터 300km/h로 달릴까? 아니다. 앞에 사고가 있을 수도, 공사 중일 수도, 차가 막힐 수도 있다. 일단 조심스럽게 출발한다.

TCP도 완전히 똑같다. 100MB짜리 파일을 한 번에 다 던지지 않는다. 상대가 감당할 수 있는지 모르기 때문이다.

식당을 생각해 보자. 손님 한 명이 왔는데 주방장이 갑자기 100접시를 한꺼번에 내온다. 테이블이 감당하지 못하고 음식이 바닥에 떨어진다. TCP는 이런 일을 싫어한다.

Slow Start — 천천히 출발, 그런데 빠르게

그래서 조금씩 보낸다. 하나 보내고 ACK를 받으면 다음엔 두 개. 또 받으면 네 개. 계속 늘려가며 길이 괜찮은지 시험하는 것이다. 이걸 Slow Start라고 한다.

이름 때문에 "천천히 조금씩 늘리나 보다" 하고 오해하기 쉽다. 사실은 매번 두 배씩, 엄청나게 빠르게 늘어난다.

그런데 패킷 하나가 사라졌다

TCP는 생각한다. "길이 막히기 시작했네." 여기서 중요한 것. TCP는 패킷이 없어졌다고 해서 인터넷 선이 끊어졌다고 생각하지 않는다. 대부분은 혼잡이라고 해석한다. 공유기나 라우터가 너무 바쁘면 패킷을 그냥 버리기 때문이다.

고속도로에 차가 너무 많으면 톨게이트가 "더 못 받겠습니다" 하고 차를 잠깐 막는 것과 같다. 그래서 TCP도 속도를 줄인다. 이걸 Congestion Control, 혼잡 제어라고 한다.

Window Size — 한 번에 볼 수 있는 범위

TCP는 계속 계산한다. "지금 얼마나 보내도 될까?" 상대도 계속 말한다. "난 지금 20개까지 받을 수 있어." TCP는 "오케이, 20개만 보낼게"라고 답한다. 조금 뒤 상대가 "이제 100개도 괜찮아"라고 하면 늘린다. 이게 Window Size다.

왜 하필 창문일까? Window에는 "한 번에 볼 수 있는 범위"라는 뜻도 있다. TCP도 창문 크기만큼 한 번에 보낸다.

더 깊이
  • 창문은 사실 두 개다. rwnd는 상대가 광고하는 수신 윈도우(Flow Control), cwnd는 내가 스스로 계산하는 혼잡 윈도우(Congestion Control). 실제 전송량은 min(rwnd, cwnd)다. 위에서 나눠 설명한 두 개념이 여기서 한 줄로 만난다.
  • 지수 증가는 영원하지 않다. ssthresh라는 문턱값에 도달하면 Slow Start가 끝나고 Congestion Avoidance로 넘어가 RTT당 +1씩 선형으로만 늘린다. 급가속 뒤 정속주행이다.
  • "손실 = 혼잡"은 알고리즘마다 다르다. 리눅스 기본인 CUBIC은 손실을 혼잡 신호로 본다. 반면 구글의 BBR은 손실 대신 실제 대역폭과 RTT를 측정해서 판단한다. 무선망처럼 혼잡과 무관하게 손실이 나는 환경에서 TCP가 억울하게 느려지는 문제를 푼 것이다.

일상과 연결해 보면

유튜브를 켜면 처음에는 화질이 낮다가 조금 지나면 1080p, 4K로 올라간다. 이유 중 하나가 바로 네트워크 상태를 계속 측정하기 때문이다. (실제로는 TCP뿐 아니라 유튜브의 적응형 스트리밍 알고리즘도 함께 동작한다.)

은행에서는 이 개념이 훨씬 중요해진다. 대량 거래 데이터를 갑자기 전속력으로 밀어 넣으면 계정계 → 중간 스위치 → 대외망 어딘가의 버퍼가 넘칠 수 있다. 그래서 TCP는 상대와 네트워크 상태를 계속 보면서 속도를 조절한다.

오늘의 핵심

TCP는 최대한 빨리 보내는 프로토콜이 아니다.

TCP는 상대와 네트워크가 감당할 수 있는 가장 빠른 속도를 계속 찾아가는 프로토콜이다.

다음 장

여기까지 오면 마지막 퍼즐이 남는다. 요즘은 "HTTP/3는 TCP를 안 쓴다"는 말이 들린다. 지금까지 TCP가 인터넷의 핵심이라고 배웠는데, 왜 최신 웹은 UDP 기반으로 가고 있을까?

Chapter 17

TCP가 있는데 왜 QUIC은 UDP를 선택했을까?

먼저 분명히 해두자. HTTP/3는 TCP를 버린 것이 아니다. TCP가 해결하지 못하는 문제를 다른 방식으로 해결한 것이다.

웹페이지 하나를 열어보자

주소창에 https://google.com을 입력하면 브라우저는 TCP 연결 → TLS 암호화 → HTTP 요청 → HTML 응답 순서로 움직인다. 여기까지는 우리가 배운 내용이다.

그런데 웹페이지는 HTML만 오는 것이 아니다. CSS, JavaScript, 이미지, 폰트, 광고, 아이콘… 요청이 수십 개, 많게는 수백 개다. 여기서 문제가 생긴다.

Head-of-Line Blocking

패킷 하나가 사라졌다고 하자. TCP는 뭐라고 했지? "순서를 지켜야 하니까, 뒤에 있는 것도 기다려."

택배차를 상상해 보자. 3번 상자가 분실됐다. 택배회사는 4번도, 5번도 전부 붙잡아 둔다. 순서를 지켜야 하니까. 문제가 보인다. 4번은 이미 도착했는데도 사용하지 못한다.

이 현상을 Head-of-Line Blocking이라고 한다. 뜻 그대로 줄의 맨 앞(Head)이 막혀서 뒤(Line) 전체가 기다리는 것이다.

웹페이지에서는 이게 특히 아깝다. 이미지 2번이 늦었다고 해서 이미지 3번까지 못 보여줄 이유는 없다. 하지만 TCP는 순서를 지켜야 하니까 기다린다.

구글의 질문

독립적인 데이터까지 같이 기다릴 필요가 있을까?

그래서 만든 것이 QUIC이다. 재미있는 점은 QUIC이 TCP를 고친 게 아니라는 것이다. UDP 위에 새로운 기능을 올렸다.

기존 HTTPS

  1. HTTP
  2. TLS
  3. TCP
  4. IP

HTTP/3

  1. HTTP/3
  2. QUIC
  3. UDP
  4. IP

"UDP는 재전송도 안 한다며?" 맞다. 원래 UDP는 아무 기능도 없다. 그래서 QUIC이 직접 만든다. 재전송, 순서 관리, 암호화, 속도 제어를 QUIC 안에서 전부 구현한다. TCP가 하던 일을 애플리케이션 계층에 가까운 곳에서 다시 만든 셈이다.

왜 그렇게까지 했을까 — 독립적인 Stream

가장 큰 이유는 Stream이다. TCP에서 HTML·CSS·이미지·광고는 결국 한 줄로 흐른다. 중간이 막히면 전부 기다린다. QUIC은 이것을 네 개의 독립된 Stream으로 본다.

이미지가 늦어져도 HTML은 계속 처리한다. 광고가 늦어져도 CSS는 먼저 적용한다. 웹페이지가 훨씬 부드러워진다.

또 하나 — 연결과 암호화를 함께 설계했다

HTTPS에 접속할 때 TCP 연결 다음에 TLS를 다시 준비했던 것을 기억하자. QUIC은 처음부터 암호화를 함께 설계했다. 연결과 암호화를 한 번에 처리하니 첫 접속도 더 빨라질 수 있다. (정확한 향상 폭은 네트워크 환경과 재연결 여부에 따라 달라진다.)

더 깊이
  • HTTP/2는 왜 실패했나. HTTP/2도 이미 스트림 다중화를 했다. 하지만 HTTP 레벨에서만 스트림을 나눴고 그 아래 TCP는 여전히 하나였다. 그래서 TCP 레벨 HOL이 그대로 남았다. QUIC은 그 문제를 전송 계층까지 내려가서 해결한 것이다.
  • QUIC도 HOL이 완전히 없진 않다. 스트림 사이의 격리일 뿐, 하나의 스트림 내부에서는 여전히 순서를 기다린다.
  • Connection ID — 잘 안 알려진 킬러 기능. TCP는 4-tuple(출발지 IP·포트 + 목적지 IP·포트)로 연결을 식별한다. 그래서 Wi-Fi에서 LTE로 바뀌어 IP가 달라지면 연결이 끊긴다. QUIC은 Connection ID로 식별하므로 끊기지 않고 그대로 이어진다. 지하철에서 영상이 안 끊기는 이유다.

그럼 TCP는 끝난 걸까?

전혀 아니다. 은행을 생각해 보자. 10만 원을 송금하는 데 무엇보다 중요한 것은 정확성이다. 패킷 하나가 사라지면 안 된다. TCP는 수십 년 동안 검증된 기술이고, 지금도 대부분의 웹 서비스(HTTP/1.1, HTTP/2), 데이터베이스 연결, 은행 시스템, 파일 전송, 이메일에서 널리 쓰인다.

QUIC은 TCP를 대체하는 존재가 아니라, 웹 환경에서 TCP의 일부 한계를 개선하기 위해 등장한 새로운 선택지다.

오늘의 핵심

TCP는 신뢰성을 최우선으로 설계된 전송 프로토콜이다.

QUIC은 그 신뢰성을 유지하면서, 현대 웹에서 중요한 지연 시간과 독립적인 데이터 처리를 개선하기 위해 UDP 위에 새롭게 설계된 프로토콜이다.
